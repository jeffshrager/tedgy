## What we did
Developed the Lincoln Text Adventure as a concrete demo project to flesh out what TedGy's inputs and outputs actually look like. No code — all design artifacts.

### lincoln_project.md
Created `docs/lincoln_project.md` — a master project plan written in Ted's voice. Teams build a playable text adventure game about Abraham Lincoln, compressed to a 3-day arc for demo purposes (each day represents a project phase). Key design choices:
- Ted's voice: guiding, not prescriptive — gives direction and observable outcomes, not step-by-step tasks
- Day 1: organize (roles, game concept, rough plan for tomorrow)
- Day 2: research + design in parallel, with a required handoff moment
- Day 3: build + play-test + debrief
- Roles are not pre-assigned; Ted lists functions that need covering, team decides role names and assignments

### Sheet mocks: three daily handouts
Created `docs/day01_sheet_mock.md`, `docs/day02_sheet_mock.md`, `docs/day03_sheet_mock.md`.

**Handout structure (applies every day):**
- Project name + day number at top
- One-sentence project description (identical every day — serves as a compass)
- Short paragraph: what we're doing today (Ted's voice)
- Widgets specific to that day
- Specific fill-in instructions embedded near each widget
- "Hand this in at end of class" footer (except Day 3, which is the last day)

**One packet per team per day.** Multi-page days (like Day 2) scan together as one unit per team.

**Day 1 widgets:**
- Role table: open columns (role name, responsibility, student name) — team fills in their own role names
- "Our game is about" fill-in (two lines — encourages more than one sentence but forces a decision)
- Tomorrow plan table (student name → what they'll do)

**Day 2 widgets:**
- Part A (research team): fact table (fact + where it appears in game), briefing notes for design team
- Part B (design team): scene map table (scene #, setting, player text, choice A, choice B), endings (2–3 boxes)
- Handoff section (whole team): what changed after research briefed design — forces reconciliation, also a useful TedGy signal

**Day 3 widgets:**
- Part A (writers): scene text boxes (one per scene, 6 provided)
- Part B (play-test log): observation table with triage column ("is this a problem to fix?"), what was actually fixed
- Part C (debrief): one thing that went well, one thing that was hard, done/not-done checkbox

### Design principles established
- Widgets constrain input to make vision parsing reliable (labeled blanks, tables, checkboxes — not free-draw)
- Observation tables include a triage column so TedGy can read team judgment, not just raw notes
- Handoff/debrief sections give TedGy signal on team cohesion and integration, not just task completion
- "No-Oz baseline": sheets drafted without OzNote influence — useful because it shows what Oz *modifies*, not what it generates from scratch. Day 1 is always Oz-free (nothing to react to yet); Days 2+ would be shaped by Oz reading the prior day's scans.
